### A-12 · HIGH · clamp `$N` — **ОПРОВЕРГНУТО (инвертировано) [исп.]**

По JS-спецификации `String.replace` (`GetSubstitution`) ссылка за пределами числа групп

поведению Python. Кроме того JS здесь же `$0` отдаёт весь матч (`applySubstitutionAll('x',['m','g1'],'$0') -> ["m"]`),
хотя JS-спецификация оставляет `$0` литералом. Предложение A-12 (`return ''` в Python)
**ухудшает** код: оно подгоняет Python под баг JS и противоречит §4.3 (где JS как раз

обоих вариантов — 404/мусорное имя файла, то есть срочности нет.

## 4. Дефекты в предложенных фиксах (главный риск аудита)

### 4.1 A-07 — патч не компилируется и течёт `.partial`
Предложено:
```python
if self.max_bytes and (downloaded_this_chunk + len(write_buffer_chunk)) > self.max_bytes:
```
`write_buffer_chunk` и `downloaded_this_chunk` — имена из MT-цикла (`_download_chunk`);
в однопоточном цикле переменные называются `chunk` и `downloaded_bytes`. Как есть —
`NameError`. Кроме того `raise IOError(...)` внутри `with open(temp_path, mode)`
уходит в `download()`-`except Exception`; удаление `.partial` делается только на
явных `return`-ветках (строки 522-524, 546-548, 556-561), поэтому аварийный выход
оставит `.partial` на диске. Правильная форма — проверять **перед записью**
(`if self.max_bytes and downloaded_bytes + len(write_buffer) > self.max_bytes:`),
удалять `temp_path` и возвращать обычный `{"success": False, …}` (как остальные
фильтры), плюс новый ключ `K.SETTING_MAX_FILE_SIZE`/`DEFAULT_MAX_FILE_SIZE`.

### 4.2 A-09 — фикс порождает невалидные URL (новый дефект, см. NF-1)
Проверено исполнением предлагаемой функции: она отдаёт `"//i.imgflip.com/abc123.jpg"`
(protocol-relative) и `"$&"`; в `upgradeMediaList` результат кладётся в `url`
**без нормализации**, тогда как двойник `processLink` такую нормализацию имеет
(`background.js`: `if (!transformed.startsWith("http") && !transformed.startsWith("//")) →
protocol + transformed; else transformed.replace(/^\/\//, "https://")`).
То есть 307+452 правила начнут «находиться», но с неполными URL. Что именно происходит
с ними дальше — измерено (§6.7, шаги 5/5b и §6.7a): Chrome такой URL **принимает** и
резолвит в `file://`, докачка кончается `interrupted`/`NETWORK_FAILED` (элемент уходит в
`failed`), а desktop падает на отсутствии схемы (`MissingSchema` / curl_cffi `InvalidURL`).
В обоих случаях — битая закачка вместо fullsize; фикс без нормализации схемы неполон.

### 4.3 A-10 + A-12 — взаимоисключающие предписания
- A-10 требует в JS `match[parseInt(num)] || "$" + num` → для `$5` при 1 группе это
  литерал `"$5"`;
- A-12 требует в Python `''` на тот же вход → `"//y/.jpg"`.
После применения обоих паритет снова разрушен, только зеркально.
- Для **двузначных** A-10 тоже неверен: JS-спецификация сначала пробует две цифры, затем
  одну (`$11` при 1 группе → группа 1 + литерал `1`), а Python это делает корректно
  (`'//x/\\g<1>1.jpg'`); `"$" + num` даст литерал `$11` — расхождение.
- `$0`: JS-двойник отдаёт весь матч, спецификация — литерал `$0`; в аудите не отмечено.
**Рекомендация:** не два точечных патча, а одна таблица векторов
(`$1`, `$11`, `$5`, `$&`, `$$`, `$0`, вложенный `#…#`, многострочный `to`) в JSON,
прогоняемая и pytest, и node-сьютом, и одна реализация `GetSubstitution`
(две цифры → одна цифра → литерал; `$&`; `$$`→`$`) в обе стороны. Это сразу закрывает
A-10, A-12 и защищает от повторного дрейфа.

### 4.4 A-13 — фикс превращает падение в молчаливую потерю закачки
`try { keepaliveAcquire(); } catch (e) { resolve({ saved: 0 }); return; }` — на
Chrome <111 попап получит «✓ Saved 0» и **ни одного скачанного файла**. Keepalive —
оптимизация; правильная ленивая правка — сделать `keepaliveAcquire`/`keepaliveRelease`
непроверяемо-безопасными (`try { chrome.alarms.create(...).catch(()=>{}) } catch (e) {}`
внутри самих функций, строки 553-560) — тогда работает и на Chrome <111, а не только
на ≥111. `minimum_chrome_version: "111"` можно добавить как второй, независимый шаг
(сознательно сужает аудиторию — это продуктовое решение, не багфикс).
Дополнительно из замера §6.7: бросок происходит **после** `_keepaliveRefs++` (строка 554),
поэтому после такого отказа счётчик остаётся завышенным навсегда — безопасный
`keepaliveAcquire` должен инкрементить только после успешного создания alarm.

### 4.5 C-02 — фикс корректный, но накапливает связи
`self._sieve_done.connect(lambda …)` внутри `_on_sieve_download` добавляет новое
соединение на **каждый** клик. Соединение надо делать один раз в `__init__`,
а поток — только запускать. Альтернатива «подешевле» (в духе проекта): оставить
синхронность, но урезать таймаут и не делать второй (mirror) запрос блокирующим.

## 5. Новые находки (в Audit.md отсутствуют)

### NF-1 · HIGH · путь обновления медиа в расширении не восстанавливает схему — фикс A-09 даст невалидные URL
**Где:** `extension/background.js` `upgradeMediaList` (≈615-660) → `sieve.js`
`applySieveRulesAll`/`applySubstitutionAll`; для сравнения рабочий двойник —
`processLink` (≈395-410) и `resolveUrl`.
**Механизм [исп.]:** поставленный sieve написан для схемо-очищенного входа
(0 правил с `^https?://` в `img`/`link`; 307 `img`-якорей «хост/путь»). Пока
`applySieveRulesAll` тестирует полный URL, такие правила не срабатывают — как только
A-09 разрешит совпадение по stripped-форме, шаблоны вида `previews$1images$2`,
`//i.$1$2.#jpg gif#`, `$1` дают строку **без схемы**:
```
proposed matcher: Imgflip-h-p → ["//i.imgflip.com/abc123.jpg","//i.imgflip.com/abc123.gif"]
```
`upgradeMediaList` кладёт это прямо в `result.url` (и далее в `chrome.downloads` и в
payload для desktop). **Проверено в реальном SW (§6.7, шаги 5 и 5b):** Chrome такой URL
**принимает** (`{url:"//i.imgflip.com/abc123.jpg"}` → `id:1, err:null`), но резолвит его
в **`file://i.imgflip.com/abc123.jpg`** — докачка доходит до
`state:"interrupted", error:"NETWORK_FAILED", bytesReceived:0`. То есть ошибка возникает
**после** старта (в момент вызова никакого `lastError` нет) — элемент молча уходит в
счётчик `failed`. Контроль: обычный `https://…` даёт `SERVER_BAD_CONTENT` (файл
скачался, но это не медиа).
Корнево-относительный `/abc123.jpg` Chrome отклоняет сразу (`err:"Invalid URL"`).
Для desktop те же строки — сразу видимый отказ клиента (замер §6.7a):
`requests → MissingSchema: Invalid URL … No scheme supplied`,
`curl_cffi → InvalidURL: curl: (3) URL rejected: No host part in the URL`.
**Решение:** один общий helper нормализации варианта (protocol-relative → `https:`,
без схемы → схема страницы), применять его там, где варианты рождаются
(`applySubstitutionAll`/`applySieveRulesAll`), и тот же helper передать в
`processLink` вместо дублирующей логики. A-09 тогда — «сматчить + нормализовать», и это
одна правка вместо двух расходящихся.

### NF-2 · MEDIUM · `$&`-семантика и `$N`-семантика не имеют единого владельца (тест закрепляет баг)

### 6.1 A-08 + B-16(b) — инъекция строки протокола [исп.]
Правило, которое само пишет строку в `Deno.stdout` и затем возвращает легальный URL:
```
run_js #1 -> 'https://evil.example/x.jpg'   (легальный ответ был 'https://legit.example/a.jpg')
run_js #2 -> 'https://legit.example/a.jpg'  <- ответ на запрос #1 достался запросу #2
```
Итог: атака не просто «портит текущий ответ», а **сдвигает весь протокол на строку** —
все последующие вызовы получают результат *предыдущего* правила (потому что `id` всегда 0
и не сверяется). Это сильнее, чем в аудите: там описана только миссатрибуция одного ответа.
**Фикс из аудита** (`'"use strict";\nconst Deno = undefined;\n' + wrapped`) проверен на
копии воркера:
```
shadow, обычное правило        -> https://legit.example/a.jpg   (т.е. правило работает)
shadow, правило с Deno.*       -> https://legit.example/a.jpg   (инъекция заблокирована)
shadow, правило с globalThis.Deno -> https://evil2.example/y.jpg (обход удался)
```
Вывод для аудита: однострочный shadow — **полезная, но не достаточная** мера;
настоящая граница — сверка `id` + отказ от посторонних строк (B-16), в идеале — протокол
на отдельном fd. Применять A-08 и B-16 одним изменением.

### 6.2 A-16 — блокировка event-loop [исп.]
```
run_js(«while(true){})») -> None за 5.02 с; heartbeat asyncio: max пауза = 5.02 с
после таймаута: _proc = None (воркер убит), следующий вызов респавнит воркер
```
Аудит прав буквально: «бюджет 5 с» — это 5 с замороженного loop (Stop, прогресс,
`completion_monitor`), и это подтверждено замером, а не рассуждением. Фикс
(`run_in_executor` вокруг обоих вызовов) — обязательный, но только вместе с B-02 (иначе
заморозка переезжает в общий дефолтный пул, который делится с закачками).

### 6.3 A-15 — блокирующая запись в stdin [исп.]
```
stdin.write(строка 21 МБ) -> вернулось за 1.70 с   (ребёнок жив)
```
То есть запись действительно блокирующая и её длительность пропорциональна размеру
HTML. Катастрофический сценарий («зависает, пока ребёнок не начнёт читать») здесь не
воспроизвёлся — happy-dom поднимается из локального кэша быстро; на холодном/неполном
кэше (B-19) блокировка станет секундами. Формулировку в аудите стоит смягчить до
«блокирует вызывающего до 2 с на 20 МБ и не ограничена по времени», механизм и фикс верны.

### 6.4 B-15 + F-06 — утечка процесса [исп.]
```
B-15: сымитирован отказ kill() -> _proc = None, а victim.poll() is None == True
      (живой deno.exe + 2 хэндла пайпа, ссылок на него больше нет)
F-06: run_js после shutdown() -> 'resurrected', _proc снова не None
      (движок воскрешает воркер, которого никто уже не убьёт)
```
Обе находки подтверждены вживую, включая то, что «чистый» (по мнению кода) shutdown
наблюдаемо оставляет работающий процесс.

### 6.5 B-17 — happy-dom без закрытия [исп.] — худшее из Deno-блока
Один воркер, страница 0,22 МБ, правило-заглушка:
```
старт:                 RSS =   45 808 KB
после  1 вызова:       RSS =  182 996 KB
после +10 вызовов:     RSS =  811 360 KB
после +50 вызовов:     RSS = 3 753 868 KB   <- 3,75 ГБ в одном процессе
```
Линейный рост: (3 753 868 − 45 808) KB / 61 вызов = **60 788 KB ≈ 59 МиБ на вызов**.
На галерее из 500 thumbnail-проб (`probe` →
`run_dom_js` на каждый) это OOM средствами одного воркера. Аудит ставит B-17 MEDIUM —
по факту это HIGH.
**Фикс из аудита API-валиден:** вендоренный `happy-dom` **15.11.7**,
`lib/window/Window.js:42` создаёт `this.happyDOM = new DetachedWindowAPI(browserFrame)`,
а `DetachedWindowAPI.close()` (строка 64) → `this.#browserFrame.page.close()`.
Значит `win.happyDOM.close()` в `finally` — рабочий вариант, и «остаточный риск №5» аудита
(«наличие API не проверено») закрывается как **подтверждено**. Желательно ещё
ограничить сам воркер: перезапускать его после N вызовов или явно освобождать окно
на каждый запрос.

### 6.6 B-18 — большие payload'ы [исп.] — не воспроизведён
```
 1,1 МБ html -> None за 0,8 с, воркер жив
 4,4 МБ html -> None за 1,7 с, воркер жив
13,1 МБ html -> None за 4,0 с, воркер жив
```
(`None` — артефакт моей тестовой заглушки: `_call_dom` принимает только список.)
Падения/убийства воркера на 13 МБ нет; время растёт линейно. То есть «взрывает RSS
воркера или роняет его по OOM» на 13 МБ не подтверждается — риск есть, но он ниже, чем
описан (реальный OOM приходит из B-17, а не из размера одной страницы). Накопление без
предела (`acc +=`) — факт по коду, и защита в пару строк полезна.
