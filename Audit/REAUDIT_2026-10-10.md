## 2. Блок R-E — расширение (MV3)

### R-E-8 · HIGH (ИЗМЕРЕНО) — онлайн-обновление sieve мертво: `import()` запрещён в ServiceWorker

`background.js` реализует C-1/Phase-4 так:

```js
_sieveUpdater = await import(chrome.runtime.getURL("sieve_updater.js"));
```

MV3 service worker **не поддерживает dynamic import** — это ограничение спецификации, а не
политика CSP. Живая проверка (headless, реальный SW, реальный popup как драйвер):

```
[step 1/2] ... (page) chrome-extension://<id>/popup/popup.html
  result: "SW answered: {"status":"error","message":"updater unavailable"}"
[step 2/2] (sw)
  result: "dynamic import FAILS: import() is disallowed on ServiceWorkerGlobalScope
           by the HTML specification. See https://github.com/w3c/ServiceWorker/issues/1356."
```

Последствия — **вся фича обновления sieve не работает ни в одном из трёх входов**:
- недельный `chrome.alarms` → `runSieveUpdate()` → `getSieveUpdater()` → `null`;
- `setTimeout(runSieveUpdate, 15000)` при холодном старте SW → то же;
- кнопка попапа «Update sieve now» → ответ `{"status":"error","message":"updater unavailable"}`.

Важно: `getSieveUpdater()` ловит исключение и лишь пишет `console.warn`, поэтому пользователь
не видит ошибки в UI — кнопка просто «ничего не делает». Комментарий в коде
(«sieve_updater.js is an ES module (importScripts cannot load it)…») фиксирует осознанный
обход, который не работает на платформе.

**Проверка на «не наша ли это среда»:** тот же запуск, тот же профиль, реальный попап отдаёт
корректный статус из того же ключа стораджа —
`sieveInfo: "Sieve: 823 rules (158 JS — skipped in popup)"`, что совпадает со статическим
подсчётом по `extension/sieve.json` (823 правила, 158 с JS-`to`). То есть измеряется реальный
продукт, а не сломанная страница.

### R-E-9 · MEDIUM (воспроизведено) — расширение игнорирует `off: 1`; выключенные правила продолжают срабатывать

Найдено при анализе взаимодействий (см. §10, цепочка 2), а не чтением одного файла.

Замер (реальный код обоих файлов, стаб только у стораджа):

```
parseSieve extracted: 780 chars | mentions off: false      <- в расширении off не читается ВООБЩЕ
round 1 -> Dead present: true | Dead.off = 1               <- mergeSieve ШТАТНО выключает удалённое правило
round 2 -> keys: A1,A2,Dead | Dead.off = 1 | A2.off = 1    <- ghosts накапливаются и не удаляются
parsed-as-ACTIVE by extension: A1,A2,Dead                 <- выключенные — В СПИСКЕ АКТИВНЫХ
ghost still active: true / true
validRuleCount(merged2): 3                                 <- обе off-правила посчитаны как годные
```

Три следствия:
1. **8 поставляемых правил с `off: 1` активны в расширении уже сегодня**, хотя десктоп их
   корректно пропускает (`site_pattern_manager.py:301` — `if rule_data.get('off')`) → расхождение
   платформ по одному и тому же файлу правил.
2. `loadSieveResPatterns()` (`background.js`, цикл `Object.entries(data)`) тоже не проверяет `off` →
   выключенные правила участвуют и в res-обнаружении полноразмерных ссылок.
3. `countJsRules` считает и выключенные — попап показывает «823 rules (158 JS)», включая мёртвые.

Это не косметика: механизм `mergeSieve` ВЫКЛЮЧАЕТ удалённые upstream-правила именно через
`off: 1` — без поддержки `off` любое обновление sieve не отключает ничего, а ghost-правила
(`off: 1`) копятся в сторадже монотонно (раунд 2 их не удалил).

### R-E-1 · HIGH (латентный) — `updateSieve` пишет `sieveRules` объектом; контракт стораджа ломается

Пока R-E-8 не исправлен, этот дефект недостижим — но он первый, что выстрелит, если
`sieve_updater.js` начать загружать.

**Контракт:** `background.js:loadSieveRules()` пишет `sieveRules: JSON.stringify(data)` (строка);
читатели: `loadSieveResPatterns()`, `handleStartScan()`, `popup.js:updateSieveInfo()` — все через
`JSON.parse`.

**Факт:** `sieve_updater.js:updateSieve()` пишет объект:
`await storage.set({ sieveRules: merged, sieveUpdateLast: Date.now() })`, где
`merged = mergeSieve(stored.sieveRules || {}, result.data)` — а `stored.sieveRules` на первом
обновлении строка, которую `mergeSieve` обходит `for (const key in oldSieve)` как объект.

**Воспроизведение** (node, реальный `updateSieve`, стаб только у `fetch`/storage):

```
updateSieve result: { status: 'updated', message: 'Sieve updated successfully' }
stored sieveRules typeof: object
JSON.parse(stored): THROWS -> SyntaxError: "[object Object]" is not valid JSON
numeric junk keys created from the string: 29
sample junk entry: {"0":"{","off":1}
```

**Почему это HIGH, а не косметика:** `try { … } catch (e) { console.warn("Sieve transform failed") }`
в `handleStartScan` обёртывает **весь** блок трансформов вместе с фолбэком
`applyResizeUpgrade` — то есть после порчи стораджа перестаёт работать и нативный
[Resize]-порт (возврат регресса ERR-7/colorsuper). `loadSieveResPatterns()` падает на
`JSON.parse` → `cachedSieveRes` остаётся пустым → res-discovery мертво. Само не чинится:
`loadSieveRules()` выходит по `stored.sieveVersion === SIEVE_VERSION` (объект truthy).

**Вывод для правки:** R-E-8 и R-E-1 надо править **вместе** — починка только R-E-8 приведёт к
тихой порче стораджа у всех пользователей.

### R-E-7 · MEDIUM (воспроизведено) — `data:`-плейсхолдеры попадают в список медиа

уйти в очередь на скачивание, где предсказуемо провалятся.

### R-C-1 · HIGH (воспроизведено дважды) — «медийный» ключ в JSON работает как чёрная дыра

`_extract_media_from_json` (`json_parser.py:110`) на каждом ключе выбирает одно из двух: если
`_is_media_key(key)` — значение уходит в `_process_potential_media` (`:123`) и **рекурсии внутрь
него нет** (`:127` только в ветке `else`). А `_process_potential_media` понимает лишь строки и
списки: словарь молча игнорируется, элемент списка-словарь учитывается только при поле `url`
(`:188`).

Замер (мой, через `ParserManager._invoke_parser` с фейковой aiohttp-сессией): контрольные
`{"images":["…pic.jpg"]}` и `{"images":[{"url":…}]}` → медиа найдено; `{"data":{…}}`,
`{"media":{…}}`, `{"images":[{"src":…}]}` и `{"data":{"images":["…pic.jpg"]}}` → **пусто**.
Совпадает с замером Claude на синтетике.

Последствие: тихая потеря всей выдачи у API, где нагрузка лежит под `data`/`media` — то есть у
большинства. Ни ошибки, ни строки в логе. Направление фикса: при медийном ключе и dict (или
list-of-dict без `url`) — рекурсия внутрь, а не только строковый разбор.

### R-C-3 · HIGH (воспроизведено end-to-end) — HTML-страница ошибки сохраняется как медиафайл

Механика: `response_head = self.session.head(…)` (`media_downloader.py:397`) →

`RequestException` (проверено запуском), а `NETWORK_ERROR_EXCEPTIONS = (RequestException,)`
(`http_engine.py:183-190`), поэтому исключение ловится как «сетевая ошибка» на `:416`
(«HEAD request failed … Will attempt GET») и поток идёт на GET. Но `response_head` **уже
присвоен**, поэтому защита `if response_head is None:` (`:469`) ложна — проверка `Content-Type`
для GET (`:470-474`) не выполняется. Та же причина снимает проверку минимального размера: она
живёт внутри HEAD-`try` (`:411-415`), где `content_length` ещё 0.

Замер (фейковая сессия, реальный `MediaDownloader.download()`, temp-каталог, 4 случая):

| Случай | Результат | На диске |
|---|---|---|
| **HEAD 403 → GET `text/html`** | **`success: True`** | **`photo.jpg`, 128 Б, начинается с `<!DOCTYPE html>`** |
| HEAD без ответа (ConnectionError) → GET `text/html` | `success: False`, «Webpage/script content» | — |
| HEAD 200 `text/html` | `success: False`, «Webpage/script content» | — |
| HEAD 200 `image/jpeg` | `success: True` | `photo.jpg`, 120000 Б |

То есть защита есть и работает — но ровно в том случае, когда HEAD **не ответил**. Если хост
отвечает 403/405, страница отказа/логина ложится на диск под расширением картинки, а загрузка
отчитывается об успехе. **Мой аудит это пропустил:** я читал этот код и счёл проглоченный

(«user modifications are never silently dropped»: `_`-правила и `off`) действовало только для
онлайн-апдейта, а релиз расширения его отменял: у пользователя оживали правила, которые он выключил,
и ghost-правила, удалённые апстримом.

**Измерено** (node-гейт `tests/upgrade_media.test.mjs`, кейс «bundle bump …», мутация `? data` вместо
`? updater.mergeSieve(...)` переводит его в красный): теперь бамп использует тот же `mergeSieve`,
`_`-правило, `off:1` и ghost выживают, новая версия бандла ставится.

### R-E-14 · INFO (прочитано) — `mergeSieve` мутирует свой вход

`for (const key in newSieve) merged[key] = newSieve[key]` раздаёт ссылки, а следующий цикл
проставляет `merged[key].off = …` — это меняет объект, пришедший **снаружи**. Сегодня безопасно
(оба вызова сразу сериализуют результат), поэтому править не стал; при третьем вызывающем
нужен `Object.assign({}, newSieve[key])`.

## 10. Взаимодействия, совокупные последствия и рекомендации

Смысл раздела: находки по отдельности безобидны, в паре — ломаются тихо. Все цепочки ниже
опираются на измерения выше; где вывод из кода, а не из запуска, это сказано.

### Цепочка 1 · R-E-8 ⊃ R-E-1: порчи в поле нет, но починка половины её создаёт

R-E-8 делает писатель недостижимым → порчи нет (измерено: `sieveRules` — `string`, `parses: true`).
Значит **миграция не нужна**, но и **чинить надо одно целое**: починка только загрузки
включает необратимую порчу (R-E-1 не самоизлечивается — `loadSieveRules` выходит по неизменному
`sieveVersion`).

### Цепочка 2 · R-E-8 → R-E-9 → рост и «живые мертвецы»

После починки R-E-8 штатный `mergeSieve` начнёт выключать удалённые правила через `off: 1`…
а расширение `off` не читает (R-E-9) → выключенное продолжает срабатывать, ghost-правила копятся
без возможности удаления. То есть **R-E-9 обязателен в той же правке, что и R-E-8**: иначе мы
включаем фичу, которая со временем делает набор правил неуправляемым.

### Цепочка 3 · включение фичи = сетевая активность на КАЖДОМ старте SW

Сейчас `setTimeout(runSieveUpdate, 15000)` — тихий no-op. После починки он станет реальным:
`updateSieve` делает 2 URL × 3 попытки = до 6 `fetch` с `AbortSignal.timeout(10000)` плюс backoff
1+2 c на URL → **вычисленно до ~66 с сетевой активности на каждом холодном старте SW**
при недоступной сети. `keepaliveAcquire` там не вызывается, поэтому воркер может умереть
посередине — но счётчик попыток вслепую остаётся.

### Цепочка 4 · R-E-8 → версия: обновление живёт только между релизами

`updateSieve` не пишет `sieveVersion`, а `loadSieveRules()` при `stored.sieveVersion !==
SIEVE_VERSION` перезаписывает сторадж встроенным файлом. После включения это значит: на каждом
релизе расширения скачанное (возможно, более новое) правило-множество молча заменяется встроенным.

### Цепочка 5 · R-E-1 (или просто промах правила) + R-E-4 = «пустой список без ошибок»

Пустой `cachedSieveRes` → discovery деградирует к `<img>`-фолбэку → находки помечаются
`linked-img`, которых нет в `FULLSIZE_SOURCES` (R-E-4) → они скрыты фильтром «Full size»,
включённым по умолчанию. Пользователь видит ноль полноразмерных без единой ошибки — самый
дорогой в поддержке класс симптомов.

### Цепочка 6 · R-E-7 внутри фильтра — маршрут зависит от классификатора URL

`data:`-элементы имеют источник `img`/`srcset` → не в `FULLSIZE_SOURCES` → в дефолтном виде их
не видно, но они уходят в очередь при «All sources» и в клавиатурном пути
(`items = fullsize.length ? fullsize : media`, `background.js`).

**Измерено** (классификаторы на реальном `data:image/gif;base64,R0lGODlhAQABAAAAACw=`):

```
is_valid_url: False | is_media_url: False | is_webpage_url: False | is_format_allowed(image): True
parser_manager branch -> 'webpage rather than media': False
```

То есть ветка «веб-страница» в `_process_media_batch` НЕ срабатывает (для этого нужен
`is_webpage_url and not is_media_url`), и мусорная запись уходит в `download_queue` как медиа.

**Прослежено по коду, но не прогнано:** запрос к `data:`-URL падает на неверной схеме (у requests
это `InvalidSchema`, подкласс `RequestException`); HEAD это молча проглотит (`response_head`
остаётся None), а GET вернёт `{"success": False, "error": "Network error: …"}`. Этот текст попадает под
`_RETRYABLE_ERROR_HINTS` ("network error"), поэтому `download()` будет повторять попытку до значения
настройки Retry Count — то есть **до ~8 неудачных запросов и ~3 с sleep на одну мусорную запись**,
плюс `files_skipped += 1` и `domain_state["failures"] += 1` **на пустом ключе домена**
(`urlparse("data:…").netloc == ""`, потому что "network error" не входит в список content-skip).
Сколько именно таких записей даёт реальная страница — не измерялось.
