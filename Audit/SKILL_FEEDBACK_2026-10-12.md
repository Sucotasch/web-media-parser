## 2. Остаток: F1 закрыт не на всех входах — `--wait-for` (MEDIUM)

**Симптом тот же, что в F1.** У флага свой цикл опроса, отдельный от `pollUntil`, и проверки
`exceptionDetails` в нём нет:

- `probe.mjs` **1121–1131** (`--target sw`) — `if (r?.result?.value)`;
- `probe.mjs` **1155–1171** (page) — то же самое, плюс `challengeInfo` на таймауте.

**Замер (оба входа, `--wait-timeout 6000`):**

```
page:  wait-for: TIMED OUT after 6247ms            EXIT=1   (ни причины, ни подсказки)
sw:    wait-for (sw): TIMED OUT after 6211ms       EXIT=1
контроль тем же флагом: wait-for (sw): true after 1ms   EXIT=0
```

Контроль важен: опрос жив, сломан именно разбор исключения — то есть это остаток F1, а не новый
дефект.

**Почему это не угол.** `SKILL.md` §«Session reuse, and driving the product» прямо предлагает этот
флаг как штатный способ ждать (`node probe.mjs --attach --wait-for '<expr>'`), и он же —
единственный способ дождаться состояния без `--script`. То есть ровно тот сценарий, ради которого
F1 и заводился («предикат с `await` выглядит как флак»), здесь воспроизводится целиком.

**Предлагаемое изменение (скетч, НЕ применено).** Вынести разбор в хелпер и позвать его из всех
трёх мест — тогда поведение перестанет расходиться между входами:

```js
// probe.mjs: один разбор на все три цикла (в pollOnce он уже есть - вынести и переиспользовать)
const evalPredicate = async (send, expression, contextId) => {
  const r = await send("Runtime.evaluate", {
    expression, ...(contextId ? { contextId } : {}), returnByValue: true, awaitPromise: true,
  });
  if (r && r.error) return { dead: true, why: r.error.message || String(r.error.code) };
  const ex = r?.exceptionDetails;
  if (ex) return { threw: true, why: `predicate threw: ${ex.exception?.description || ex.text}` };
  return { value: r?.result?.value };
};
```

```js
// и в двух циклах --wait-for (1121-1131 и 1155-1171) - та же ранняя остановка, что уже есть
// в pollUntil (1260-1265)
const t0 = Date.now();
let ok = false;
while (Date.now() - t0 < WAIT_TIMEOUT) {
  const res = await evalPredicate((m, p) => s.send(m, p), WAIT_FOR, null);
  if (res.threw) {
    console.log(`  wait-for: FAILED at once - ${res.why}`
      + (/await/.test(WAIT_FOR) && !/async/.test(WAIT_FOR) ? " (top-level await? wrap the predicate in (async () => …)())" : ""));
    process.exitCode = 1;
    break;
  }
  if (res.value) { ok = true; break; }
  await sleep(300);
}
```

**Как проверить фикс:** `node probe.mjs --ext <dir> --headless --url about:blank --wait-for
"(await 1) > 0" --wait-timeout 6000` — ожидаем мгновенный `FAILED at once` с `SyntaxError` и
exit 1, а не 6-секундный `TIMED OUT`; тот же вызов с `--target sw` — то же самое.

### M2 · LOW · новое правило не задокументировано

Фикс трактует как фатальное **любое** исключение, а не только компиляционное. Замер выше: предикат
`document.querySelector('#nope').textContent === 'x'` (элемента ещё нет — обычный шаблон ожидания)
теперь падает сразу с `TypeError`, а не ждёт появления элемента. Решение защитимое — бросающий
предикат почти всегда баг теста, и молчаливый 30-секундный таймаут хуже, — но в `SKILL.md` этого
правила нет (поиск `FAILED at once` пуст). Стоит строчка вида: «шаг с `wait`/`until`, который
бросил, падает сразу — пишите предикат через `?.` (или оборачивайте риск в `try`), иначе ждать
нечего».

### M3 · LOW · формулировка handover'а при битом `until` (уже замерено)

`ask` идёт через тот же `pollUntil`, поэтому битый `until` выходит по ветке `threw`, и дальше идёт
текст про человека. Замер (видимое окно, `until: "(await 1) > 0"`):

```
  wait: FAILED at once - predicate threw: SyntaxError: Unexpected number (top-level await? wrap the predicate in (async () => …)())
ASK UNANSWERED: SELF-TEST: this must fail before any handover text
  (no challenge markers - the predicate simply is not true yet)
  the run ends here (the browser was closed). …
```

Строка `FAILED at once` стоит перед этим и всё объясняет, поэтому это не дефект, а формулировка: для
сломанного предиката уместнее сказать «предикат `until` бросил исключение», а не «человек не отозвался».

## 4. Второй проход (2026-10-12): то, что в первом отчёте стояло как «не проверял»

Первый отчёт заканчивался списком непроверенного. Досчитал — и два пункта из этого списка оказались
дефектами, а не просто пробелами.

### N1 · HIGH · resume после `--ask-keep` не возвращает вас на ту же страницу

Сам hold работает: `ASK_KEEP_EXIT=3` (вызывающая сторона вернулась — до этого момента текст скилла
утверждает, что так не бывает), браузер жив, запись в реестре полная
(`"9829": {"pid": 13384, "port": 9829, "extName": "Web Media Parser", …}`), а
`--close --port 9829` отвечает `closed the kept instance … state entry removed` и очищает реестр.

А вот **resume — нет**. `--attach --script <тот же файл> --from 1` открывает НОВУЮ вкладку с тем же
`url` и опрашивает её, а не удержанную страницу. Замер: предикат
`typeof window.__loadedAt === "number" && (Date.now() - window.__loadedAt) > 30000` был бы истинен
мгновенно на удержанной странице (она жила > 30 с), но прогон дал `wait: TIMED OUT after 4071ms` →
`ASK UNANSWERED`, exit 1, а вкладок стало 3 → 4 (старая осталась на месте). Значит состояние
документа, которого ждал человек, на resume не сохраняется (cookie/профиль — сохраняются, страница —
нет). Для challenge/consent-шага это ровно то место, ради которого handover и существует: resume
заново упирается в тот же гейт.

Плюс вторая ловушка на том же пути: если между hold и resume воркер MV3 ушёл в idle, resume падает
раньше — `(no service worker for "Web Media Parser" after 60s)` → `ERROR: extension SW not found`,
exit 1, браузер оставлен. Документированная гипотеза («открыть страницу расширения, чтобы разбудить
воркер») **верна** — я её проверил: `PUT /json/new?chrome-extension://<id>/popup/popup.html` →
`service workers 1`, после чего тот же resume пошёл дальше. Но инструмент этого не делает сам, а текст
ошибки отправляет искать stale profile (факт 11) — то есть уводит в другую сторону.

Предложение: (1) на resume переиспользовать существующую вкладку с этим `url`, а не открывать новую;
(2) в `--attach` перед ожиданием воркера будить его (extension page) и только потом ждать.

### N2 · MEDIUM · `--attach --eval` не попадает на нужную страницу

- без `--url`: оценка уходит в постороннюю страницу — `result: "about:blank"`;
- с `--url <fixture>`: попадает на fixture, но открывает ЕЩЁ одну вкладку (targets 3 → 4), а её
  `JSON.stringify` теряет ожидаемые поля, потому что это свежий документ.

То есть состояние удержанной страницы так не прочитать и не изменить — при этом ответ приходит
правдоподобный, и агент может принять его за факт.

### N3 · MEDIUM · Firefox: расширение не ставится вовсе, и FF умеет оставить сироту

- `--browser firefox --dry-run` и отказ `--target sw|ext` (exit 2, «privileged scope») — как
  задокументировано.
- Живой прогон: `[ff] run failed: webExtension.install: invalid web extension Could not install
  Add-on: background.service_worker is currently disabled. Add background.scripts.` Причина в
  манифесте проекта: MV3, `"background": {"service_worker": "background.js"}` (v1.3.1), а Firefox
  такие временные аддоны не ставит без фолбэка `background.scripts`.
  **Исправлено в расширении 2026-10-12 (этот сеанс):** в манифест добавлен
  `background.scripts` (`shared.js, sieve.js, sieve_updater.js, background.js`) плюс
  `browser_specific_settings.gecko.id`, а вызов `importScripts` в `background.js:12` обёрнут в
  `if (typeof importScripts === "function")` — в фоне Firefox такой функции нет.
  Проверено на FF 157.0.1: `[ff] installed Web Media Parser -> web-media-parser@sucotasch`, exit 0.
  Контроль на ТОМ ЖЕ браузере (копия расширения с исходным манифестом):
  `Could not install Add-on: background.service_worker is currently disabled` — значит помог именно
  манифест, а не обновление FF между прогонами. Chrome не пострадал: тот же E2E дал exit 0,
  8 элементов, попап 5/5 и 8/8, 8 загрузок `complete`.
  **Не проверено в FF:** попап (скан/загрузка) — бэкенд не пускает в extension-контексты
  (`--target sw|ext` отвергается с причиной «privileged scope»), а UUID аддона из профиля не
  достать (см. N4). Проверено ровно столько: аддон ставится, загружается без ошибок JS
  (в FF ошибка расширения ВАЛИТ прогон — exit 0 здесь содержателен), и реальная страница открывается.
- Сирота: после первого FF-прогона инструмент напечатал `[ff] browser killed (pid 5232), run finished`,
  но дерево Firefox (11 процессов; родитель 20400, главный 18244) осталось живо и слушало BiDi на
  **9796**, и следующий FF-прогон умер на `session.new: session not created Maximum number of active
  sessions`. То есть «browser killed» — не доказательство (hazard #9: спавненный pid — только
  стартер). Воспроизвелось 1 раз из 3.
- `--browser firefox --close --port 9796` сироту не лечит: `the registry has no instance on port 9796
  (refusing to hunt by image name)` — FF-инстансы в реестр не попадают. Сироту я нашёл по порту
  (`netstat -ano` → 9796 → 18244) и снял адресно.

Предложение: регистрировать FF-инстансы в state-файле (pid — со стороны протокола/порта), чтобы
`--close` до них доставал.

### N4 · MEDIUM · отравленный профиль = необработанный EPERM (голый стек)

**Причина уточнена 2026-10-12.** В первой редакции я написал, что виновато смешение профилей
Chromium и Firefox в одном каталоге. Это неверно: состояние воспроизводится на **всех трёх**
каталогах, включая два FF--only (`ff-fix-1`, `ff-fix-2`, оба использовал только Firefox). То есть
EPERM даёт сам прогон Firefox (вероятнее всего — не снятые хендлы при убийстве дерева): каталог после
прогона нельзя ни читать (`extensions.json`, `prefs.js`, любые файлы → EPERM), ни писать, ни
переименовать — «снести профиль и перезапустить» из Safety rails недоступно, помогает только новый
`--profile`. Отдельная мелочь: каталог профиля Chromium (`<repo>/.ext-dev-loop/extension/profile`) был
использован и FF-бэкендом (так решил ff-dry-run) — UI-профили двух браузеров в одном каталоге лучше не
держать, даже если причиной EPERM это не было.

На таком профиле прогон падает так (пример с каталога Chromium, который зацепил и FF):

```
Error: EPERM: operation not permitted, open '…\.ext-dev-loop\extension\profile\browser-stderr.log'
    at file:///C:/Users/sucot/.agents/skills/ext-dev-loop/scripts/probe.mjs:528:17
Node.js v24.19.0
```

exit 1, без диагноза. Свежий `--profile` работает (прогон exit 0). Предложение: (1) FF не должен
делить каталог профиля с Chromium (формат разный; сейчас там лежит смесь их файлов); (2) при EPERM на
логе — новое имя файла или внятная ошибка «profile dir is not writable, pass a fresh --profile».

### N5 · LOW · шаг без `url` читает `about:blank`

`--script` из двух page-шагов, где `url` есть только у первого: шаг 2 печатает `url: about:blank` и

### N6 · LOW · противоречие в тексте handover'а

При `--attach --script` неудовлетворённый `ask` печатает `the run ends here (the browser was closed)`,
а следом — `browser left running [after --script]`. Браузер действительно остаётся: текст врёт.

### N7 · LOW · конфликт портов не диагностируется

Чужой слушатель на `127.0.0.1:9827` **без** SO_REUSEADDR (node): прогон напечатал строку запуска
(`pid 7644, port 9827`) и на этом встал — за 180 с ни attach, ни ошибки, ни подсказки. Для сравнения:
слушатель, который делит порт (python, `SO_REUSEADDR`), запуску не мешает вообще (прогон exit 0), так
что «порт занят» надо моделировать именно без SO_REUSEADDR.

Хуже того: браузер из этого зависшего прогона **пережил** вызывающую сторону — PID 7644 остался жив и
слушал `[::1]:9827` (нашёл его, только когда перестал фильтровать адрес по `127.0.0.1`; мои проверки
чистоты не видели его несколько итераций). Урок и для скилла, и для проверяющего: смотреть обе семьи
адресов и весь диапазон, иначе сирота невидим.

### N8 · LOW–MEDIUM · активация вкладки в отдельном шаге не доживает до клика

Первый E2E-сценарий (мой) активировал вкладку фикстуры шагом `sw`, а кликал по `#scan-btn` следующим
шагом — и получил `0 items` (пусто в `#media-list`, `Save (Chrome)` задизейблен, `chrome.downloads` —
пусто). Рабочий вчерашний сценарий делает иначе: переактивирует целевую вкладку **внутри того же
eval, что и клик**, и его шаг отдаёт `active: "http://127.0.0.1:9811/index.html"`, после чего скан даёт
8 items. Похоже, attach к странице попапа делает активной саму страницу попапа, и
`chrome.tabs.query({active:true,currentWindow:true})` из неё возвращает попап.

Рецепт §«E2E with downloads, offline» появился именно ради этой ловушки, но советует активировать вкладку
«из шага `sw`» — а в моём прочтении это оказался отдельный шаг. Стоит дописать прямо: активируйте
целевую вкладку **в том же eval, что и клик**.

### H8 · LOW–MEDIUM · `wait` ничего не проверяет, если предикат уже истинен: многофазный гейт зелёный «сам по себе»

Мой гейт «закрыть и открыть попап» сначала шёл так: фаза 1 (скан) → `wait: status === done` →
фаза 2 (перезагрузка) → `wait: <список не пуст>`. Прогон дал `wait: true after 1ms` **оба** раза:
второй `wait` увидел список, оставшийся от первой фазы (перезагрузка по факту не состоялась —
см. ниже), и гейт отчитался зелёным, хотя не проверил ничего.

Причина молчания была конкретная и стоит строчки в SKILL.md:
**`chrome.tabs.query({})` из воркера не отдаёт URL extension-страниц**
(`url: null` без `tabs`-permission), поэтому «найти вкладку попапа по URL» не находило её и
перезагрузка не вызывалась:

```
result: {"error":"tab not found","urls":[null,"http://127.0.0.1:9811/popup-reopen.html",null]}
```

Рецепт, который работает: extension-страница называет свою вкладку сама —
`chrome.tabs.getCurrent()` (id не требует разрешений) — и отдаёт её воркеру через
`chrome.storage.session`; а ожидание второй фазы делается **edge-triggered** (метка
`window.__x`, выставленная до перезагрузки, обязана исчезнуть). Тогда пропущенная перезагрузка
валит прогон таймаутом, а не проходит молча. Просится в SKILL.md одним абзацем:
«в многофазных прогонах жди ИСЧЕЗНОВЕНИЯ старого состояния; `wait` по уже-истинному предикату —
это no-op, а не проверка».
